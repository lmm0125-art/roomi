## 1. 검증 목적

기업이 제시한 원래 문제는 **"수업이 없는 날 아이들이 DOROBUS에 들어오지 않는다"** 였다.
본 검증은 우리가 만든 콘텐츠가 그 문제를 실제로 줄였는지를 **수치로** 확인하는 것을 목적으로 한다.

검증할 가설:
> **H1.** 매일 수행할 수 있는 과제와 성장 장치가 있으면, 아이는 수업이 없는 날에도 접속한다.
> **H2.** 로봇을 꾸미는 소비처가 있으면, 획득한 셀을 실제로 사용한다.
> **H3.** 연속 방문 보상(7일 순환)이 반복 접속을 만든다.

## 2. 지표 정의

> ⚠️ 지표 정의는 **구현 코드와 정확히 일치**해야 한다. 같은 이름의 값이 두 가지로 계산되면
> 검증 자체의 신뢰성을 잃는다. (본 프로젝트에서 실제로 발생했던 문제)

| 지표 | 정의 | 계산식 | 단위 |
|---|---|---|---|
| **재접속률** | 가입일부터 오늘까지의 경과일수 중 **실제 활동한 날의 비율** | `활동일수 ÷ 경과일수 × 100` | % |
| **체류시간** | 하루 단위로 **정책 상한(40분)까지만 인정**한 합계 | `Σ min(일별 체류초, 2400초) ÷ 60` | 분 |
| **일당 평균 체류** | 위 합계 ÷ 활동일수 | — | 분 |
| **셀 사용량** | 상점에서 실제로 지출한 셀 합계 | `Σ |음수 거래|` | 셀 |
| **과제 제출률** | 하루에 배정된 과제 중 실제 완료한 비율 | 실제 프로토타입은 "1인당 완료 과제 수"로 측정 | 건/인 |

### 정의상 주의
- **재접속률은 매일 접속하면 100%** 가 된다. (첫 방문일도 활동일수에 포함)
  → "가입 후 며칠 중 며칠 왔는가"를 그대로 읽으면 된다.
- **체류시간에 40분 상한을 두는 이유**: 브라우저 탭을 켜 두기만 한 시간이 그대로 누적되면
  "하루 40분 제한"이라는 정책과 모순되는 값이 나온다. **정책과 지표를 일치시켰다.**
- 상한을 적용하지 않은 원값도 함께 보관한다(`playMinRaw`) — 필요 시 근거로 제시 가능.

## 3. 측정 방법

### 3.1 집계값 (개인정보 없음 — 인용·발표용)
```
GET /api/public/stats
→ {"participants":N, "avgReturnRate":%, "avgPlayMinutes":분,
   "avgActiveDays":일, "avgQuests":건, "avgGames":회,
   "definition":"재접속률 = 활동일수 ÷ 경과일수 ...", "note":"개인 식별 정보는 포함하지 않는 집계값입니다"}
```
- **키가 필요 없다.** 개인 식별 정보를 포함하지 않으므로 그대로 발표 자료에 인용할 수 있다.
- 데모·시연·테스트 계정은 **자동 제외**된다.

### 3.2 개별 데이터 (분석용)
```
GET /api/admin/export.csv?key=<ADMIN_KEY>
→ CSV (엑셀 한글 호환 BOM 포함) 20개 컬럼
   id, nickname, created_at, level, exp, streak, balance,
   activeDays, spanDays, returnRate, playMin, playMinRaw, visits,
   quests, games, parts, earned, spent, hasRobot, firstVisit
```
- 관리자 키가 설정되지 않은 환경에서는 **503을 반환**(fail-closed) — 실수로 공개되지 않게 했다.

### 3.3 수집 시점
| 항목 | 방법 | 시점 |
|---|---|---|
| 접속 | 마이룸 진입 시 1회 기록 (새로고침 횟수가 아님) | 자동 |
| 체류시간 | 페이지 이탈 시 `sendBeacon` 1회 + 서버 중복 방지 | 자동 |
| 셀 거래 | 모든 증감을 `cell_tx` 에 기록 | 자동 |
| 과제 완료 | `quest_logs` (과제) / `game_logs` (미니게임) 분리 기록 | 자동 |

> **모든 데이터는 학생 계정 단위**로 기록된다 (회사 권고 4번).

## 4. 검증 방식 — 시나리오 기반 내부 검증

> **외부 사용자를 모집하지 않는다.** 팀 내부 계정과 데모 시드로 **기능 동작과 지표 집계의 정합성**을 확인한다.
> 실사용자 대상 효과 측정은 최종 발표 이후 과제로 남긴다(7장).

### 4.1 검증 환경
| 항목 | 내용 |
|---|---|
| 계정 | 팀 내부 계정 3개 + 데모 계정 1개 |
| 역할 구분 | 신규(가입 직후) · 성장(3일차) · 이탈(5일 미접속) |
| 데이터 | 실제 서비스와 동일한 DB — `/api/admin/export.csv` 로 추출 |
| 기간 | 3일 × 시나리오 2회전 |

### 4.2 시나리오 (각 1회 이상 수행)
| # | 시나리오 | 확인하는 것 |
|---|---|---|
| 1 | 가입 → 로봇 제작 → 첫 우편 수령 | 지급·차감이 `cell_tx` 에 남는가 |
| 2 | 매일 과제 제출 → 같은 날 재제출 | UNIQUE 로 중복 지급이 막히는가 |
| 3 | 미니게임 1회 → 같은 종류 재도전 | 종류별 1일 1회 제한 |
| 4 | 상점 구매 (잔액 충분/부족) | 차감 정확성, 부족 시 거부 |
| 5 | 공작소 재색칠·성격 재생성 | 1일 1회 제한, LLM 실패 시 프리셋 대체 |
| 6 | 수업 코드 출석 (정답/오답/재시도) | 주 1회 제한, +100셀 |
| 7 | 5일 미접속 후 복귀 | 스트릭 리셋·복원, 재접속률 계산 |

### 4.3 측정 — 화면과 데이터가 일치하는가
| 확인 대상 | 방법 | 판정 기준 |
|---|---|---|
| 재접속률 | 리포트 화면 값 vs CSV 재계산 | 오차 0 |
| 체류시간 | `visits.duration` 합 vs 리포트 | 오차 0 |
| 셀 사용량 | `cell_tx` 합 vs 잔액 변화 | 오차 0 |
| 과제 제출률 | `quest_logs` 건수 vs 리포트 | 오차 0 |

### 4.4 윤리·개인정보
- **외부 사용자 없음** → 보호자 동의 절차 불필요
- 계정은 닉네임만 사용, 실명·연락처·생년월일 수집하지 않음
- 검증 종료 후 계정 삭제 API 로 데이터 제거 (`🔄` → 서버 DB 실제 삭제)

## 7. 한계와 주의

1. **외부 사용자 검증을 하지 않았다** — 효과 크기(재접속률이 몇 % 올랐다)를 주장하지 않는다.
   이번 단계에서 확인한 것은 **"지표가 의도대로 계산된다"** 까지다.
2. **표본이 팀 내부 3계정** — 통계적 의미 없음. 경향 해석도 하지 않는다.
3. **기간이 짧다** — 3일. 7일 순환 보상은 1회전도 관찰되지 않는다.
4. **자기 검증 편향** — 만든 사람이 테스트하므로 놓치는 불편이 있다.
5. **체류시간의 성질** — 탭을 켜 둔 시간이 섞일 수 있어 40분 상한을 적용했다.
6. **외부 검증 계획** — 학교·기업 일정과 맞물려야 하므로 최종 발표 이후 과제로 남긴다.
