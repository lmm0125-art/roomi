# 개선점 보고 V9 — 아직 다루지 않은 영역 (제품·체험 관점)

> **작성**：2026-10-07
> **범위**：Babylon CDN 과 과정 라인(기획서·사례조사·발표자료 등)은 요청대로 **제외**.
> 지금까지의 보고(V2~V8)가 **버그·정합성** 중심이었다면, 이번은 **"아이가 실제로 무엇을 느끼는가"** 관점이다.
> **방법**：코드 전수 확인 + 임시 DB 실측(`/tmp/rvB.db`, roomi.db 미접촉)

## 一、🔴 높은 가치 — "만들어 놓았는데 아이가 못 느끼는" 것들

### 1. 성장 단계가 **로봇 외형에 전혀 반영되지 않는다** (실측 확인)

```
function buildRobotModel(scene, parent, c, template, extraParts, matFactory)   // app.js:543
  호출부 3곳 모두: buildRobotModel(..., effectiveColors(robot.template, robot.palette), robot.template, ...)
                                                                                    ↑ 색과 템플릿만
```

`stage`(아기/청소년/성체)는 **서버 라벨과 텍스트로만** 존재한다. 클라이언트에서 `stage` 는 단 한 곳(app.js:397)에서 문자열로 변환될 뿐, 3D 로 넘어가지 않는다.

**→ Lv.1 아기와 Lv.9 성체의 로봇이 3D 상에서 완전히 동일하게 보인다.**

회사가 말한 기대효과 ①은 **「성장 경험 — 아이 스스로 '어제보다 나아졌다'고 느끼는 것」**이다. 그런데 아이가 매일 보는 로봇은 **전혀 변하지 않는다.** 유일한 변화는 옆의 "Lv.5 아기" 글자와 XP 바다. `3-와이어프레임.svg` 에 「Lv · 성장단계」라고 적어 두었지만, 실제로는 **라벨만**이다.

**수정(반나절)**：`buildRobotModel` 에 `stage` 를 넘기고, 단계별로
- 아기: 머리 크게·몸 작게·안테나 짧게 (비율 1.15 : 0.85)
- 청소년: 현재 비율
- 성체: 몸 크게·안테나 길게·눈 약간 작게

색은 아이가 칠한 그대로 두고 **비례만** 바꾸면 되므로 그림 재작업이 필요 없다. 레벨업 순간에 3D 가 눈에 띄게 변하는 연출(스케일 트윈)까지 붙이면 **"어제보다 나아졌다"가 문자 그대로 눈앞에서 일어난다.**

> 지금까지의 개선이 "안 되는 것을 되게 만드는" 일이었다면, 이것은 **"이미 있는 것을 아이가 느끼게 만드는"** 일이다. 투자 대비 체감 효과가 가장 크다.

### 2. 스트릭 보상표가 **아이에게 보이지 않는다** (실측)

```
server.js:500  const STREAK_REWARDS = { 1:10, 2:15, 3:25, 4:35, 5:50, 6:60, 7:100 };
public/app.js  STREAK_REWARDS 언급 0건
```

아이는 "🔥 3일 연속"만 본다. **내일 4일차에 +35셀, 7일차에 +100셀이 온다는 사실을 모른다.**

스트릭이 재방문을 만드는 원리는 **"예고된 보상"**이다. Duolingo 가 일주일치 보상을 전부 늘어놓는 이유가 그것인데, 이 프로젝트는 **가장 강한 재방문 장치를 숨겨 놓았다.** 보상을 받은 뒤에야 얼마인지 알 수 있다.

**수정(1~2시간)**：`/api/growth/me` 에 `streakTable` 과 `todaySlot` 을 추가하고, 마이룸에 **7칸 달력**을 그린다.
```
🔥 3일 연속   [10][15][25][35][50][60][100]
                ✓   ✓   ✓   ▲내일   …    …    ★7일
```
"내일 오면 +35셀, 7일 채우면 +100셀" 이 보이면 **내일 다시 올 이유**가 문장이 아니라 화면으로 생긴다.

### 3. **자랑·전시 루프가 없다** (실측)

자체 `2-셀흐름도.svg` 에 **「전시·자랑」 단계를 그려 놓았는데 구현이 없다.**
- 랭킹/순위: 실질 0건 (유일한 hit 은 무관한 주석)
- 마이룸 방문·친구: 0건
- 공유·저장: 0건

**아이가 자기 로봇을 누구에게도 보여줄 수 없다.** 실제 DOROBUS 에는 타자게임 1등 = 셀 획득 경로가 있고(설명회 자료에 명시), 마이룸 방문 문화가 있다. 즉 **회사가 이미 가진 재미 요소인데 이 프로토타입에는 없다.**

평가기준 ④趣味의 "동기"와 ⑤體系性의 순환 구조에서 **마지막 고리(자랑하고 싶어서 다시 온다)** 가 비어 있다.

**최소 구현(2~3시간, 서버 불필요)**
- 「내 로봇 자랑하기」 버튼 → 3D 캔버스를 PNG 로 저장(아이가 카톡·부모님께 보낼 수 있음)
- 또는 미니게임 **일일 랭킹 top 5** — `game_logs` 에 점수가 이미 다 있어서 API 한 개면 된다

### 4. 부품 보너스 상한 **+10 은 도달 불가능**, 실제 상한은 **+6** (실측)

```
server.js:454  const PART_BONUS_PER = 2, PART_BONUS_MAX = 10;
server.js:456  SELECT COUNT(*) ... WHERE i.type='part'      ← '행 수' 기준
시드: type='part' 아이템은 3종뿐 (나사60·리본80·부스터120)
```

실측:
```
안테나 리본 구매 → partBonus = +2
로켓 부스터 구매 → partBonus = +4
나사 장식 구매   → partBonus = +6
교환으로 나사 장식 qty 1→2 로 늘려도 → 여전히 +6   ← 같은 행의 수량만 증가
```

그런데 **UI·주석·`2-셀흐름도.svg` 는 모두 "부품 1개당 +2 (최대 +10)" 이라고 광고**한다. 도달할 수 없는 값을 광고하는 셈이다.

게다가 **부품 구매 동기가 3개에서 끝난다.** "부품을 사면 과제 보상이 올라간다"는 소비 유인인데, 3종을 다 사면 더 이상 오르지 않는다. 경제가 2~3일에 포화되는 문제를 **더 빠르게** 만든다.

**수정(10분, 택1)**
- ① `COUNT(*)` → `SUM(qty)` 로 바꾸면 교환으로 늘린 중복 부품도 보너스에 반영된다
- ② 부품 종류를 5종으로 늘린다(상한 +10 이 실제로 도달 가능해짐)
- ③ 광고를 "최대 +6" 으로 정정

## 二、🟡 중간 — 체험의 질

### 5. **소리가 전혀 없다** (실측 0건)
`audio` / `sound` / `AudioContext` — app.js·index.html 모두 0건. 초등 대상에서 **청각 피드백은 재미의 큰 부분**이다. 보상·정답·버튼에 소리가 없으면 장면이 밋밋하게 느껴진다.
**수정(30분)**：WebAudio 오실레이터로 삐- 소리 몇 개. **에셋 0바이트, 다운로드 0** — 앞서 기호(●▲■)를 유니코드로 해결한 것과 같은 방식이다.

### 6. **자동 테스트가 없다** (package.json 에 `start` 만)
지금까지 **5라운드 연속 회귀**가 있었다:
`(o.qty||1)` → `PAL_BASE` 스코프 → `_starting` 소실 → 기호 중복 → 지표 불일치.

**전부 "경계값" 유형**이고, **스모크 테스트 한 개면 대부분 걸렸다**(최대 난이도·최대 반복·수량 0).
```
npm test  →  임시 DB 로 서버 기동 → 불변식 약 15개 검사
   · 구매 3회 → 교환 → 조각 0개인가
   · 8일차 스트릭 보상 > 0 인가
   · 체류시간 2회 보고 시 증가하지 않는가
   · admin/public/CSV 재접속률이 동일한가
   · 기억게임 전 단계에서 기호가 고유한가
   · 실효 소비처 ≤ 일일 수입 × N 인가
```
**2시간 투자**로 남은 기간의 모든 수정이 안전해진다. 지금까지 매 라운드 제가 손으로 하던 검증을 자동화하는 것과 같다.

### 7. **저사양 기기 대응이 없다** (실측 0건)
- `adaptToDeviceRatio:true` (레티나에서 4배 픽셀) + `MeshBuilder` 호출 **71회** + `ShadowGenerator(1024)` + `DefaultRenderingPipeline`
- `setHardwareScalingLevel` 폴백 **0건**, FPS 감시 **0건**

학교 태블릿·크롬북에서 발표하면 **버벅이거나 발열**할 수 있다. 지금은 "되는 기기에서는 되고, 안 되는 기기에서는 2D 로 강등" 뿐이다.
**수정(1시간)**：시작 후 3초간 FPS 측정 → 기준 미달이면 ① `hardwareScalingLevel` 상향 ② 그림자 끄기 ③ AA 끄기. 화질을 조금 포기하고 **부드러움을 지킨다.**

### 8. **첫 실행 온보딩이 없다** (실측 0건)
닉네임 입력창에 곧바로 떨어진다. 실제 DOROBUS 는 **첫 로그인 5단계 가이드**가 있고, 그게 설명회 자료에도 들어 있다. `renderSteps()` 로 "오늘의 4단계"는 있지만, **처음 온 아이에게 "여기서 뭘 하는 곳인지" 설명하는 층이 없다.**
**수정(1시간)**：첫 실행 시 3단계 오버레이 — ①로봇을 만든다 ②매일 과제로 셀을 모은다 ③부품으로 꾸민다. 회사 플랫폼과 같은 패턴이라 발표에서 "기존 UX와 일관된다"고 말할 수 있다.

### 9. **주간·시즌 콘텐츠가 없다** (실측 0건)
계획서가 명시적으로 물은 **「회차·시즌·난이도로 확장 가능한가」**에 대한 답이 화면에 없다. 경제가 2~3일이면 포화되는데, **주말 한정 아이템**이나 **주간 교체 진열** 하나면 "이번 주에 들어가 봐야 할 이유"가 생긴다.
**수정(2시간)**：`items` 에 `week_only` 플래그 → 해당 요일/주차에만 노출. 서버 로직은 몇 줄이다.

## 三、우선순위 (체감 효과 ÷ 소요 시간)

| 순위 | 항목 | 소요 | 왜 |
|---|---|---|---|
| 1 | **성장 단계 → 로봇 외형 반영** (一-1) | 반나절 | 회사 기대효과 ①이 **눈에 보이게** 된다. 이미 있는 기능이 아이에게 도달한다 |
| 2 | **스트릭 7칸 달력** (一-2) | 1~2시간 | 재방문 장치를 **예고**로 바꾼다. 가장 싸게 재접속률을 건드린다 |
| 3 | **부품 보너스 상한 정정** (一-4) | 10분 | 도달 불가능한 값을 광고 중. 소비 유인이 3개에서 끊긴다 |
| 4 | **자동 테스트** (二-6) | 2시간 | 남은 기간 모든 수정의 안전망. 지금까지 회귀가 5번 났다 |
| 5 | **자랑하기 / 일일 랭킹** (一-3) | 2~3시간 | 자체 셀 흐름도의 마지막 고리를 채운다 |
| 6 | **효과음** (二-5) | 30분 | 에셋 0, 체감 즉시 |
| 7 | **저사양 폴백** (二-7) | 1시간 | 발표장 기기 리스크 제거 |
| 8 | **첫 실행 온보딩** (二-8) | 1시간 | 실제 플랫폼과 UX 일관성 |
| 9 | **주간 로테이션** (二-9) | 2시간 | 확장성 질문에 화면으로 답한다 |

**1~4번 합계 약 6시간**이고, 그중 1·2·3번은 **"이미 만든 것을 아이가 느끼게"** 하는 작업이다.

## 四、총평

지금까지 여덟 번의 검증은 대부분 **"코드가 말한 대로 도는가"** 를 봤다. 이번에 본 것은 **"아이가 그것을 느끼는가"** 이고, 결과는 이렇다.

> **만들어 놓았는데 아이에게 닿지 않는 것이 세 개 있다.**
> - 성장 단계를 만들었지만 **로봇은 안 변한다** (라벨만)
> - 스트릭 보상을 만들었지만 **예고가 안 보인다** (받아야 안다)
> - 부품 보너스를 만들었지만 **+6에서 멈춘다** (광고는 +10)

셋 다 **버그가 아니다.** 코드는 정상 동작한다. 다만 **기획 의도가 화면까지 도달하지 못했다.** 그리고 이 셋은 정확히 회사가 말한 기대효과 ①(성장 경험)과 재방문 이유에 직결된다.

기술적으로는 이미 충분히 앞서 있다. 남은 시간에 **기능을 더 얹는 것보다, 만들어 둔 것이 아이 눈에 보이게 하는 편**이 발표에서 훨씬 강하다. 위 1~3번은 **하루면 끝나고**, 그 하루가 "성장 경험"이라는 문장을 **아이 눈높이의 사실**로 바꾼다.
