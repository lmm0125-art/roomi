# 기술 스택 적응 방안 — 루미(RooMi)

> 대상: ㈜도로 DOROBUS 플랫폼에 루미 모듈을 얹을 때의 이식 계획
> 작성 기준: 현재 저장소 코드(`server.js` 38 API · 15 테이블 · Babylon.js 7 · Express 5)

---

## 0. 먼저 확인해야 하는 것 (우리가 모르는 부분)

지금까지 확인된 것은 **"3D는 Babylon.js, 서버는 Node/Express 계열"** 이라는 점입니다.
아래 5개는 확인 전까지 **가정**으로 두고, 확인되는 즉시 이 문서를 갱신합니다.

| # | 확인 항목 | 왜 필요한가 | 가정값(임시) |
|---|---|---|---|
| 1 | 마이룸 3D 엔진·버전 | Babylon 7 문법 유지 가능 여부 | Babylon.js 7 |
| 2 | 프런트 프레임워크 | 바닐라 UI를 그대로 쓸 수 있는지 | React 계열 |
| 3 | 인증 방식 | 자체 토큰 → 회사 세션/SSO 교체 범위 | JWT 또는 세션 쿠키 |
| 4 | DB 종류 | SQL 이식 난이도 | MySQL 또는 PostgreSQL |
| 5 | 배포 환경 | 컨테이너 여부, 정적 자산 CDN | 컨테이너 + CDN |

> 이 5개가 정해지면 **작업량이 3일에서 3주까지** 벌어집니다. 그래서 8번 항목(기업 확인)이 일정의 선행 조건입니다.

## 1. 현재 우리 스택 (사실)

| 레이어 | 현재 | 비고 |
|---|---|---|
| 3D | **Babylon.js 7 (CDN)** | 절차적 메시(코드로 생성), GLB 미사용 |
| 프런트 | **순수 HTML/CSS/JS** | 프레임워크·번들러 없음, 4파일 |
| 백엔드 | **Node 22 + Express 5** | 의존성 1개(`express`) |
| DB | **node:sqlite 내장** | 15 테이블, UNIQUE 8종 |
| 인증 | 자체 토큰(헤더) + 관리자 키 | 관리자 키 미설정 시 503 |
| API | **REST/JSON 38개** | `/api/...`, 모두 JSON |
| 배포 | 단일 Node 프로세스 + 정적 파일 | DB는 파일 1개 |

**이식에 유리한 점**: 표준 SQL만 사용 (`strftime`·`julianday`·`INSERT OR IGNORE` 미사용).
**이식 시 손봐야 할 점**: `AUTOINCREMENT` 15곳, 자체 토큰 인증, CDN 의존.

## 2. 공통분모와 차이

```
            회사(가정)                    우리 프로토타입
3D      Babylon.js  ──────────── 같은 계열 ────────────  Babylon.js 7
서버     Node/Express ──────────── 같은 계열 ────────────  Node/Express 5
DB      MySQL/Postgres ─────── 다름(스키마 이식) ───────  node:sqlite
프런트   React 계열 ─────────── 다름(UI 재작성) ───────  바닐라 JS
인증     회사 계정 ─────────── 다름(교체) ─────────────  자체 토큰
```

즉 **로직·스키마·3D는 살리고, 껍데기(프런트·인증·DB 엔진)만 갈아끼우는** 구도가 됩니다.

## 3. 통합 방식 3안

| | A. 임베드 (권장) | B. API 분리 | C. 풀 머지 |
|---|---|---|---|
| 방식 | 마이룸/공작소 화면 안에 **iframe·WebView**로 루미 모듈 삽입 | 우리 서버만 남기고 **API 제공**, 화면은 회사 프런트가 그림 | 화면을 회사 프레임워크로 **재작성**, 서버는 서비스로 유지 |
| 프런트 작업 | 거의 없음 | 중간 | 큼 |
| 서버 작업 | 인증 연동만 | 인증 + API 계약 정리 | 인증 + API + 배포 |
| 기간(추정) | **3~5일** | 1~2주 | 3~4주 |
| 장점 | 가장 빠름, 롤백 쉬움, 발표 후 바로 시연 가능 | UI 일관성, 성능 | 완전한 제품화 |
| 단점 | UI 이질감, 모바일 제스처 이슈 | 화면 개발 부담이 회사로 | 일정 리스크 최대 |
| 추천 시점 | **중간발표 이후 1차** | 파일럿 | 최종 제품 |

> 발표에서는 **A로 붙이고, B로 넓히고, C는 최종 단계**라고 말하는 것이 가장 현실적입니다.

## 4. 레이어별 치환표

### 4.1 3D (가장 이식성이 좋은 부분)

| 항목 | 지금 | 회사 스택에서 |
|---|---|---|
| 로딩 | CDN `<script>` | 번들러 모듈 import (`@babylonjs/core`) |
| 로봇 | 절차적 메시(코드 생성) | **GLB 교체 가능** — 파츠 슬롯(head/body/arms/legs/accessory) 유지 |
| 조명·그림자 | DirectionalLight + ShadowGenerator(1536) | 동일 API, 품질 등급만 조정 |
| 후처리 | DefaultRenderingPipeline | 동일 |
| 상호작용 | 클릭 픽킹 + 말풍선 | 동일, 회사 UI 레이어로 대체 가능 |

**핵심**: 로봇은 `buildRobotModel()` 한 곳에서 만들어지고, 색은 팔레트 객체(`c.head`, `c.body` …)로만 주입됩니다.
→ 회사 아티스트가 만든 GLB를 넣어도 **같은 슬롯 이름만 맞추면** 나머지 코드는 그대로 돕니다.

### 4.2 프런트

| 지금 | 이식 |
|---|---|
| 4개 HTML + `app.js` 2,800줄 | 화면 단위로 컴포넌트 분해 (마이룸/공작소/상점/우편함/리포트) |
| `fetch('/api/...')` 직접 호출 | 회사 HTTP 클라이언트로 교체 (인터셉터·에러 처리 통일) |
| 상태 = 전역 객체 `state` | 회사 상태관리로 이관 (또는 모듈 스코프 유지) |

### 4.3 인증

| 지금 | 이식 |
|---|---|
| 가입 시 토큰 발급 → `Authorization` 헤더 | 회사 SSO/세션으로 교체, **`users.id` 매핑 테이블 1개 추가** |
| 관리자 API: `X-Admin-Key` | 회사 RBAC(운영자 롤)로 대체, 키 미설정 시 차단 로직은 유지 |

> 학생 계정이 회사에 이미 있으므로 **자체 회원가입은 끄고**, 최초 로그인 시 `users` 행을 자동 생성하는 방식이 안전합니다.

### 4.4 DB (SQLite → MySQL/PostgreSQL)

| 항목 | 조치 |
|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` (15곳) | MySQL: `AUTO_INCREMENT` / PG: `GENERATED ALWAYS AS IDENTITY` |
| `TEXT` 날짜 문자열(`YYYY-MM-DD`) | 그대로 사용 가능(권장) 또는 `DATE` 로 전환 |
| UNIQUE 8종 | **그대로 이식** — 게임 규칙 강제가 DB에 있으므로 엔진이 바뀌어도 유지 |
| 인덱스 | `CREATE INDEX` 동일 문법 |
| 마이그레이션 | `CREATE TABLE` DDL 1파일 + 시드 1개로 분리 (현재 코드에서 추출) |

**주의**: `UNIQUE(user_id, day, kind)` 같은 복합 유일 제약이 **로직의 핵심**입니다. 이걸 애플리케이션 코드로 옮기면 동시 요청에서 뚫립니다. 반드시 DB 제약으로 유지하세요.

### 4.5 API · 운영

| 항목 | 조치 |
|---|---|
| 38개 엔드포인트 | 경로 유지, 에러 포맷만 회사 규격으로 통일 |
| 중복 요청 | 이미 UNIQUE로 차단, 응답 코드만 규격화(409) |
| 레이트 리밋 | 회사 게이트웨이 정책에 위임 |
| 개인정보 | 닉네임만 저장(실명·연락처 없음) — 현 설계 유지 |
| 플레이 제한 | 하루 40분 상한, 서버에서 계산(클라이언트 조작 불가) |

## 5. 마이그레이션 4단계

| 단계 | 기간 | 하는 일 | 끝났을 때 확인 |
|---|---|---|---|
| **1. 계약 확정** | 2~3일 | 5개 확인 항목 회신, 인증·DB 확정 | 통합 방식(A/B/C) 결정 |
| **2. 3D·화면 이식** | W9–11 | Babylon 모듈화, 마이룸을 회사 셸에 임베드 | 회사 계정으로 마이룸 진입 |
| **3. 데이터 이전** | W12–13 | DDL 변환, 시드, 지표 재계산 검증 | 지표 4종이 기존 수치와 일치 |
| **4. 제품화** | W14–15 이후 | 프런트 머지, RBAC, 배포 파이프라인 | 운영자 페이지로 콘텐츠 편집 |

## 6. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| 회사 스택이 우리 가정과 다름 | 일정 2~3주 증가 | 8번 확인 항목을 **1주 안에** 회신받기 |

## 7. 발표용 30초 답변 (KR)

> "저희는 회사 스택과 **같은 계열**로 만들었습니다. 3D는 Babylon.js, 서버는 Node/Express이고, DB만 내장 SQLite라서 스키마를 그대로 옮기면 됩니다.
> 이식은 세 단계입니다. 먼저 마이룸을 **모듈로 임베드**하고, 다음에 API로 넓히고, 마지막에 화면을 회사 프레임워크로 머지합니다.
> 로봇은 코드로 만들었지만 **파츠 슬롯만 맞추면 회사 GLB로 교체**되도록 해 두었습니다.
> 다만 엔진 버전·프런트 프레임워크·인증 방식 세 가지는 확인이 필요해서, 8번 항목으로 요청드렸습니다."
