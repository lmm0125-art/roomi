# 루미(RooMi) —系统性审查报告

> 审查对象：`roomi/`（server.js / app.js / index.html）
> 基准文档：`DOROBUS-IC-PBL-执行方案.md`（企业课题要求）+ `docs/과제수행계획서.md`
> 审查日期：2026-10-03

## 一、整体评估结论

### 1.1 结论摘要

**技术完成度合格，玩法完成度不足。**

原型在工程侧已经跑通了「登录 → 造机器人 → AI 生成性格 → 每日任务 → 赚 셀 → 商店消费 → 报表」这条完整闭环，AI 双通道降级（Gemini 4 级模型链 + DeepSeek 备份 + 预设台词兜底）、经济防重复（唯一索引 + 条件 UPDATE 原子扣款）、39 处MeshBuilder 参数全量审计，这些基础设施质量**高于学生原型的一般水平**。

但对照需求文档，有**三个致命缺口**：

| # | 缺口 | 依据 |
|---|---|---|
| ① | **付费装饰品（decor）购买后完全无效** | 花了 140 셀 买的东西，在游戏里看不到任何东西 |
| ② | **成长系统整体缺位** | 企业要求的期待效果第 ① 项就是「成长经验」，当前等级/经验/连续登录/成就**全部为 0** |
| ③ | **效果验证的数据源不可信** | `체류시간` 字段永远为 0，`재접속률` 被刷新技术性放大，而这是步骤 6 明确要求验证的指标 |

外加一条**合规缺口**：目标用户是小学高年级~初中生，评价细则明文要求「安全·个人信息·防沉迷」，当前实现为 **0**。

### 1.2 三条核心循环的完整性判定

需求文档要求的核心循环是 `접속 → 사용 → 보상 → 재접속`：

```
   접속(登录/打开)
     ↓
   사용(涂色→造机器人→喂食/夸奖/答AI问)  ← ⚠️ 6天后内容枯竭
     ↓
   보상(每日 65 셀 + 随机1个零件)
     ↓
   재접속  ← ❌ 断裂：无长期目标、无 streak、无成长
```

**判定：循环在「보상」环节是通的（防重复发钱做得很扎实），但「사용」和「재접속」两处断裂。**

- 6.2 天买齐全部商品 → 之后无任何购买动机
- 喂食/夸奖点击 100 次和点击 1 次，机器人外观、状态、体验**完全相同**
- 没有任何跨天累积的成长痕迹

这直接对应评价细则里的两条失分项：
> 「有'日/周单位想再玩一次'的理由（目标·奖励·变化）吗？」→ **否**
> 「难度与奖励成比例吗？」→ **否（难度恒定为 0）**

### 1.3 严重度分布

| 严重度 | 逻辑层 | 玩法层 | 合计 |
|---|---|---|---|
| 🔴 高 | 4 | 4 | **8** |
| 🟡 中 | 5 | 4 | **9** |
| ⚪ 低 | 3 | 2 | **5** |

## 二、核心流程与状态流转梳理

### 2.1 现有流程图

```
[시작화면]  닉네임 입력
     ↓ POST /api/user  (토큰 발급 + visits 1행 INSERT + 신규이면 100셀)
[자동로그인]  localStorage(uid,nick) → POST /api/user  ★매 로드마다 visits 중복 INSERT
     ↓
     ├─ 로봇 있음 → [마이룸]
     └─ 로봇 없음 → [만들기]  → POST /api/robots (성격 생성 + 50셀 + 랜덤 부품 1개)
                                ↓
                          [마이룸] ──────┬─ POST /api/interact (feed/praise) → LLM 대사
                                        │        ↓ (퀘스트 미완료 시)
                                        │   POST /api/quest/complete → 셀 지급
                                        ├─ POST /api/quest/answer (AI 미션 1일 1회) → LLM 반응
                                        ├─ 상점 → POST /api/shop/buy → inventory
                                        │        ★type='part' 만 /robots/me 에 반영
                                        │        ★type='decor' 는 어디에도 반영 안 됨
                                        └─ 리포트 → GET /api/board/me
```

### 2.2 状态与数据流

| 状态 | 存储位置 | 生命周期 | 问题 |
|---|---|---|---|
| `state.user` | 前端内存 + localStorage | 会话 | `cell_balance` 双写（前端自行 +50） |
| `state.robot` | 前端内存 | 会话 | 造完不可改（`robots` 表有 user_id 唯一索引） |
| `state.parts` | 前端内存 | 会话 | 来自 `/robots/me`，**只含 part** |
| `state.quests` | 前端内存 | 会话 | `{list, done}`，但初始值是 `[]`（类型不一致） |
| 零件外观 | 内存 mesh | 每次重建 | `rebuildRobot` 重建，decor 永不参与 |
| 방(props) | 硬编码 | — | 不读 inventory |

### 2.3 模块依赖与耦合点

```
app.js (1337行, 단일 파일, 전역 state)
  ├── robotSVG()      ← 2D 미리보기 (机器人结构真源)
  ├── effectiveColors() ← 3D용 색 매핑 (robotSVG와 규칙 중복 정의 ★)
  ├── buildRobotModel()  ← 3D 本体 (대형 함수, 4 템플릿 if-else)
  ├── attachParts()      ← 零件装配 (part + decor 혼합, 타.Template 파라미터 의존)
  ├── createRoomBase() / buildRoomProps() ← 방 (하드코딩)
  └── startBabylon() / buildPreviewScene()← 3D 엔진 관리

server.js (496行)
  ├── LLM 체인: callGemini → callDeepSeek → robot_lines 프리셋
  ├── generatePersonality() ← 색→성격 결정론 + LLM 인사말
  ├── ensureQuests() / getQuestsFor() ← 날짜별 퀘스트 + 유저별 미션 배정
  └── grantCell() / authUser() ← 경제 + 인증
```

**主要耦合风险**：`effectiveColors()` 与 `robotSVG()` 分别维护一份配色合并规则，3 处默认值（`DEFAULT_PAL` 在 app.js 出现 2 次）。改动一处会漏另一处 → 2D/3D 表现不一致。

## 三、改进清单（按优先级排序）

### 🔴 P0 · 高严重度

---

#### 【P0-1】付费装饰品购买后完全不生效 —— 付费内容欺骗

- **影响程度**：🔴 高
- **涉及文件**：`server.js:393`（`/api/robots/me`）、`public/app.js:746`（`buildRoomProps`）、`app.js:448`（`attachParts`）

**问题描述**
商店上架 2 个装饰品（`별 스티커` 40셀、`선물 상자` 100셀，合计 140셀），但：

1. `/api/robots/me` 的 parts 查询带 `AND i.type='part'` 过滤 → decor 永远不出现在返回里
2. `buildRoomProps()` 是完全硬编码的家具摆件，**不读 inventory**
3. `attachParts()` 只会收到 part 列表

结果：孩子花 140셀 买的装饰品，**在游戏里看不到任何东西**。商店卡片却明晃晃标着「방 장식」。

这同时**摧毁了需求文档的核心论点**——`셀 흐름` 里「消耗处」必须是可见的收获，否则「生产→消耗→再接入」根本转不起来。

**改进建议**
```javascript
// server.js:393 —— 移除 type 过滤，改为分类返回
const parts = db.prepare(`SELECT i.name, i.type FROM inventory v
  JOIN items i ON i.id=v.item_id WHERE v.user_id=?`).all(u.id);
// 按 type 分组返回：{ parts:[...], decors:[...] }

// app.js —— buildRoomProps(scene, M, ownedDecors) 接收已购装饰品清单
// 별 스티커 → 벽면贴纸 위치에 배치
// 선물 상자 → 바닥(책상 옆)에 배치
```
最小改动版本：即使不做 3D 摆放，也要在 `마이룸` 侧栏做一个「보유 장식」清单+缩略图，让购买有可见回报。

#### 【P0-2】成长系统完全缺位 —— 未达成期待效果 ①

- **影响程度**：🔴 高
- **涉及文件**：`server.js`（users 表）、`app.js`（전체 화면）

**问题描述**
`grep -rci "level|experience|achievement|streak|연속"` → **server.js: 0 / app.js: 0**。

企业文档明确要求三个期待效果，第①就是**「成长经验 — 孩子自己感到'比昨天进步了'」**，评价细则也点名：

> 「有'日/周单位想再玩一次'的理由（目标·奖励·变化）吗？」

当前实现中，**跨天累积的成长痕迹是零**：机器人的外观、等级、心情、经验都不随时间变化。唯一的跨日变化只有「今天的新问题」。

**改进建议（最小可行成长线，1~2 天工作量）**

| 追加项 | 实现 | 成本 |
|---|---|---|
| **Lv. 레벨** | `users` 表加 `level`/`exp`，누적XP = quest(10) + 미션(20) + 로봇완성(30) | 极低 |
| **연속 방문 (streak)** | `visits` 已有数据，按 `date` 去重计连续天数，UI 显示 🔥N | 极低 |
| **로봇 성장 단계** | 3 阶段（아기→청소년→성체）：Lv 구간에 따라 몸 비례/눈 크기/안테나 길이 변화 | 低 |
| **칭호系统** | 3일 연속→` faithfulness.json` 累积称号（首日 새싹/3일 토끼/7일 곰） | 低 |
| **도감(收集册)** | 5개 부품 보유 시 시각화 完成度 → 상점 재방문 유도 | 低 |

`robot_lines` 表已按 `personality × situation` 组织，**天生就是为成长阶段台词准备的**，只要加一个 `growth_stage` 维度即可复用。

#### 【P0-3】效果验证指标的数据源不可信

- **影响程度**：🔴 高
- **涉及文件**：`server.js:355-359`（`/api/visit`）、`server.js:75-80`（`visits` 表）、`app.js`（无调用）

**问题描述**

1. **`/api/visit` 端点存在但前端从未调用** —— `grep "api/visit" public/app.js` 无结果
2. visits 行**只在 `POST /api/user` 时插入**，而自动登录 `init()` 每次页面刷新都调 `/api/user`
   → **`visitCount` 实际统计的是「页面刷新次数」，不是「접속次数」**
3. `visits.duration` 字段**从未被任何代码写入**，永远为 0 → `체류시간` 指标恒为 0

而这两个正是需求文档步骤 6 明确要求验证的指标：
> 「先定指标，再验证（评价细则点名）：**재접속률 / 체류 시간 / 셀 사용량 / 과제 제출률**」

**改进建议**
```javascript
// app.js — 真实 접속 1회 = 페이지 로드 1회
navigator.sendBeacon?.('/api/visit', JSON.stringify({})) 
  || fetch('/api/visit',{method:'POST',headers:{'X-Token':tk},body:'{}',keepalive:true});

// app.js — 세션 종료 시 체류시간 기록 (visibilitychange + pagehide)
const t0 = Date.now();
addEventListener('pagehide', ()=>{
  const sec = Math.round((Date.now()-t0)/1000);
  navigator.sendBeacon?.('/api/visit/duration', JSON.stringify({seconds:sec}));
});

// server.js — 탈퇴/이탈 판정용 지표 추가
reconnectRate = 1 - newUsers/totalUsers   // 신규 유저 비율로 재접속률 근사
```
另建议**在 `visits` 表加 `UNIQUE(user_id, date)`** 用于 streak，并把「접속」定义为「마이룸 진입」而非「 페이지 로드」。

#### 【P0-4】无防沉迷 / 家长锁 / 内容安全

- **影响程度**：🔴 高
- **涉及文件**：`app.js`、`index.html`、`server.js`（均无实现）

**问题描述**
`grep -rci "parent|家长|제한시간|playtime"` → **全部 0**。

评价细则明文：
> 「考虑了小学~初中的**安全·个人信息·防沉迷**吗？」

目标用户是小学高年级~初中生，当前实现的**全部**风险点：

| 风险 | 现状 |
|---|---|
| 无使用时长限制 | 儿童可无限时长游玩 |
| 家长控制 | 无 |
| AI 输出内容安全 | 依赖 prompt 约束，**输出无过滤**（`generatePersonality` / `/api/quest/answer` / `/api/interact` 的 LLM 返回直接入库并展示） |
| 个人信息 | 昵称明文存储、无脱敏、无删除机制（`btn-reset` 只清 localStorage，**DB 里的数据仍在**） |

**改进建议**
1. **家长门（简易）**：首次进入时弹一个「부모님 승인」算术题（30以内乘法），通过后设置时长上限（如 40 分钟），到点柔和提示休息
2. **输出过滤**（必做，成本低）：LLM 返回后跑一次黑名单/长度/敏感词校验，不通过则回退预设台词。当前 prompt 里写着「안전하고 건전한 표현만 사용한다」但无强制层
3. **数据删除**：`btn-reset` 补一个 `DELETE /api/user` 真正清库（演示环境合规）

#### 【P0-5】经济系统 6.2 天饱和，之后完全空转

- **影响程度**：🔴 高
- **涉及文件**：`server.js:112-118`（seedItems）、`app.js`（UI 无目标引导）

**问题描述（已量化）**

| 项 | 数值 |
|---|---|
| 每日最大收入 | 20(feed) + 15(praise) + 30(AI 미션) = **65 셀** |
| 全商品总价 | 40+60+80+100+120 = **400 셀** |
| 首次一次性收入 | 100(welcome) + 50(로봇완성) = **150 셀** |
| **全勤买齐耗时** | **(400-150)/65 + 1 ≈ 5 天** |

**第 6 天起，商店里所有东西都买得起、也都不缺，孩子没有任何理由再打开。** 而这正是需求文档的原始 Pain Point（「孩子登录天数很少」）——原型**没有解决它，反而在 6 天后复现了它**。

同时，奖励与难度**完全脱钩**：`feed`（点一下按钮）= 20 셀，`AI 미션`（写一段话）= 30 셀，都是 0 难度，评价细则的「难的任务给大奖励」无从谈起。

**改进建议（按性价比排序）**

1. **立刻做 · 扩大消费处**（堵住 6 天断崖）
   - 上架 **可重复购买的外观染色**（换色不换形），单价 20~40 셀 —— 填色本身就是本作核心动作，复购合理
   - 上架 **季节/纪念日限定皮肤**（12월 크리스마스 등），制造「再来看看」的周期性理由
2. **加随机性**（提升次日打开动机）
   - 每日登录抽 1 个「零件碎片」（3 个碎片合成 1 个零件）→ 集齐驱动力
   - 连续登录奖励递增：`1일차 10셀 → 3일차 30셀 → 7일차 100셀 + 한정 부품`
3. **难度分级**（呼应评价细则）
   - `feed`（点击）= 10 셀
   - `AI 미션`（书写）= 30 셀
   - 新增 `포관상 상자`（3 秒内抓住移动的光点）= 50 셀
   - 新增 `장부 맞추기`（记忆序列）= 80 셀
4. **零件的实际作用**：目前零件**只有外观作用，无任何数值收益** —— 建议至少给一句「加速/幸运」之类的软性加成文案，让孩子知道买了有用

#### 【P1-1】feed / praise 可无限触发，无冷却与次数限制

- **影响程度**：🟡 中（兼有资源风险）
- **涉及文件**：`app.js:1130-1144`、`server.js:400-421`

**问题描述**
两个互动按钮**没有任何限制**，任务完成后仍可无限点击。每次点击都会：
1. 调用 LLM 生成新台词 → **消耗 LLM 配额**（每日上限 490 次，`LLM_DAILY_LIMIT`）
2. 触发一次 `jumpRobot` 动画

**风险叠加**：一个孩子狂点 490 次就能耗尽当天的 Gemini 全链配额，触发 10 分钟降级；**多用户共享服务时会互相影响**。演示场景下如果遇到孩子连续点击，AI 台词会突然变成预设——这正是评价细则里「AI 品质达不到让孩子满意的水准」的担忧点。

**改进建议**
```javascript
// 서버: 인터랙션 일일횟수 제한 추가
// user_interact_logs(user_id, date, situation) UNIQUE(user_id,date,situation)
if(次数 >= 5) return res.json({line: robot.greeting, limited:true});
// UI: 버튼에 3초 쿨다운 + "오늘 다했어!" 상태 표시
```

#### 【P1-2】余额在前端硬编码 +50，服务端与前端可能不一致

- **影响程度**：🟡 中
- **涉及文件**：`app.js:196`、`server.js:376-383`

**问题描述**
```javascript
// app.js:196
state.user.cell_balance = (state.user.cell_balance||0) + 50;  // ★ 하드코딩
```
而 `POST /api/robots` 的响应**不返回 `balance`**，只返回 `reward:{cell:50}`。前端选择自己加。

**风险**：一旦服务端调整奖励值、或请求部分成功（机器人建了但 grantCell 失败），前端余额立即失真。演示中会直接显示错误数字。

**改进建议**
```javascript
// server.js:383 — 응답에 실제 balance 포함
res.json({ robotId, personality, greeting, desc, reward:{cell:50, part:item.name},
            balance: db.prepare('SELECT cell_balance FROM users WHERE id=?').get(u.id).cell_balance });
// app.js:196 — 하드코딩 제거
state.user.cell_balance = j.balance; setBalance(j.balance);
```

#### 【P1-3】AI 미션 生成 5 个问题却只给 1 个用，LLM 成本浪费

- **影响程度**：🟡 中
- **涉及文件**：`server.js:270-298`、`server.js:303-305`

**问题描述**
```javascript
const MISSION_POOL_SIZE = 5;   // 5개를 생성
// 하지만 pickMission(uid, missions) → missions[uid % missions.length]  ★ 1개만 배정
```
5 个问题存在库里，**每个用户只看到 1 个**（按 uid 取模）。剩下 4 个只有不同 uid 哈希命中时才被看到。

由于演示场景通常只有几个测试账号，**实际每天有 4/5 的 LLM 生成成本被浪费**，且孩子每天只回答一个问题——与「每天 3 种方式」的原始策略不符。

**改进建议**
