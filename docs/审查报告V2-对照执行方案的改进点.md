## 二、🔴 高危问题（均已实测或逐行验证）

### 二-1｜부품 조각（shard）没有任何兑换通道 —— P0-1「付费无回报」同类缺陷复发

- **代码承诺**：`server.js:167` 注释写明「부품 조각: 모으기(collect) 동기 — **3개 모이면 부품 1개와 교환**」
- **实际情况**：全树检索 `exchange|craft|combine|교환` → 服务端仅该注释 1 处，客户端 **0 处**。**不存在任何兑换端点**。
- **实测**：
  ```
  shard item: {"id":10,"name":"부품 조각","type":"shard","price":20,"consumable":1}
  구매 → HTTP 200 balance=90 ; 재구매 → HTTP 200 balance=70
  /api/robots/me  shards=["부품 조각"]  parts=[]     ← 买了 2 个，部件仍是空
  ```
- **后果**：孩子花 20 셀/个买碎片，永远无法使用。**与前次审查判为「必须最先修」的 P0-1 是同一类缺陷**（付费内容欺骗）。评价细则「셀 获得处与消耗处是否与既有财货流咬合」直接失分。
- **最小修复**：新增 `POST /api/shop/exchange`（3 shards → 1 random part），`/api/robots/me` 返回 `shardProgress`。约 0.5 天。

### 二-2｜색칠 스킨（skin）购买后无任何外观变化

- **实现情况**：`state.skins` 在 app.js 中**仅 3 处赋值 + 1 处列表渲染**：
  ```
  9 / 163 / 206 : 赋值        1955: ...state.skins.map(n=>({ n, kind:'색칠 스킨' }))  ← 唯一读取处：打印名字
  ```
  **未参与** `robotSVG()` / `effectiveColors()` / `buildRobotModel()` / `attachParts()` 任一渲染路径。
- **购买路径验证**：`buyItem()` 1740-1749 只在 `decorChanged` 时调 `rebuildRoomDecor()`，skin 不属于 decor → 不触发；随后 `rebuildRobot()` 只吃 `state.parts`。
- **后果**：4 种皮肤 × 30 셀，可无限复购——这是新增的**主力消耗处**，却完全不产生可见回报。孩子会立刻发现"买了没用"。
- **最小修复**：让 skin 真正改色（皮肤 = 解锁一套配色/一键换色），正好贴合本作核心动作"칠하기"。约 0.5–1 天。

### 二-3｜经济饱和从 6.2 天缩短到 2–3 天（原痛点被更快复现）

实测 `/api/items` + 代码内奖励常数：

| 项              | 数值                                                  |
| -------------- | --------------------------------------------------- |
| **有效**消费处（一次性） | 부품 80+120+60=260 · 장식 40+100=140 → **400 셀**        |
| 无效消费处          | skin 120（无效果）· shard 20（无兑换）                        |
| 每日收入           | 任务 3 种 80（含部件满额 +10）+ 미니게임 60~160 = **140–240 셀/日** |
| 首周一次性收入        | 가입 100 + 로봇완성 50 + streak 1~7일 295 = **445 셀**      |

→ **400 셀 ÷ 140~~240 셀/日 ≈ 2~~3 天买齐全部有效内容**（前次审查测算为 6.2 天）。  
评价细则「有'日/周单位想再玩一次'的理由（目标·奖励·变化）吗？」→ **仍然是否**。

**根因不是"东西太少"，而是"能反复花钱且有意义的地方 = 0"**。修复方向应是**循环型消耗处**，而非继续加一次性商品：

1. skin 真正生效（二-2）→ 立刻获得一个无限且有效的消耗处
2. shard 兑换上线（二-1）
3. 引入**周/赛季轮换限定品**（公司真实商店就是 가챠 + stamp-board 十连保底结构，可直接对接）
4. 或下调收入 / 上调价格

### 二-4｜连속방문（streak）第 8 天起断崖 —— 实测复现

`server.js:483`：`const STREAK_REWARDS = { 1:10, 2:15, 3:25, 4:35, 5:50, 6:60, 7:100 };`  
`server.js:514`：`if(streak !== streakBefore && streak in STREAK_REWARDS) streakBonus = ...`

**第 8 天起 `8 in STREAK_REWARDS` 恒为 false → 此后永远 0 奖励**，而 streak 计数器继续涨（界面显示 🔥8、🔥9……）。

**实测**（临时库）：

```
신규 로그인 → streak=1  streakBonus=10  balance=110
어제 방문 streak=7 상태에서 재접속 → streak=8  streakBonus=0
잔액 110 → 110  (차액 0셀)
```

→ **孩子连续 8 天回来，第 8 天什么都没得到**。streak 是"每天回来"的唯一机制，它在习惯刚要形成时失效。

- **最小修复**：改为 7 日循环（`STREAK_REWARDS[((streak-1)%7)+1]`），或第 8 天起给递增/固定奖励。约 3 行。

### 二-5｜체류시간 被放大 2–4 倍 —— 实测复现（步骤 6 核心指标再次不可信）

**前端重复上报**（app.js:185-199）：

```js
function reportDuration(){
  const sec = ...;
  try{ if(navigator.sendBeacon) navigator.sendBeacon('/api/visit/duration', ...{seconds:sec}...); }catch(e){}  // 第1次
  try{ fetch('/api/visit/duration', {...body, keepalive:true}); }catch(e){}                                    // 第2次，同一个 sec
}
addEventListener('pagehide', reportDuration);
addEventListener('beforeunload', reportDuration);   // ← 两个事件都会触发
```

**服务端无条件累加**（server.js:534）：`UPDATE visits SET duration = duration + ? WHERE id=?`（无幂等键）

**实测**：同一段 100 秒上报 2 次 → `duration: 100 → 200`  
**真实浏览器**：`pagehide` 与 `beforeunload` 双双触发 → 单次会话最多 4 次写入 → **最多 4 倍虚高**。

后果：리포트 的 `playMinutes` / `avgMinutes` / 7 日趋势图全部不可信。**P0-3 要解决的正是"체류시간 不可信"，修复后换了种方式失真。**

- **修复**：`let _reported=false;` 守卫 + `sendBeacon`/`fetch` 二选一 + 去掉一个监听器。

### 二-7｜🔴 기억 순서 미니게임：第 7 阶段起**数学上无法通关**（游戏性归零）

```js
1422: const MEM_COLORS = [ … 8 色 … ];          // 只有 8 个颜色
1562: const MEM_BASE_PAD = 2;
1577: const show = mm.level + MEM_BASE_PAD;      // 第7阶段 → show = 9
1584: const palette = MEM_COLORS.slice(0, show); // ★ slice 上限 = 8 → 实际只有 8 格

1596: stage.innerHTML = mm.colorOf.map(()=>'<i class="pad"></i>').join('');  // 棋盘 = 8 格
1610: const cur = pads[mm.seq[k]]; if(cur) …    // pads[8] === undefined → 该步永不点亮
```

**逐阶段推演（用实际常数）**：

| 단계    | show = level+2 | 棋盘格数 = min(show,8) | 序列最大索引 | 可通关?        |
| ----- | -------------- | ------------------ | ------ | ----------- |
| 1–6   | 3–8            | 3–8                | ≤7     | ✅           |
| **7** | **9**          | **8**              | **8**  | ❌ 索引 8 无对应格 |
| 8–9   | 10–11          | 8                  | 9–10   | ❌           |

- 序列中值为 8 的那一步**永远不会点亮**；孩子只有 8 个格子可点，**永远无法在第 8 步给出正确输入** → `memPick` 必然走到 `memFail`。

- **这是该游戏第三次出现"根本玩不了"**：10-03 日志已记录过"인덱스 공간 불일치 / 순서 고정 / 동시 점등"三个连锁 bug 导致游戏不成立。**教训没有被固化——这次是棋盘容量与序列长度不一致，与上次同源。**
- **最小修复**：`const show = Math.min(MEM_COLORS.length, mm.level + MEM_BASE_PAD);`，同时把等级上限与 UI 文案对齐（约 1 行）。

### 二-8｜🔴 기억 순서：答对后 620ms 内再点一下 → 被判"答错"（孩子会连点）

`memPick`（1617-1640）在 `n === mm.seq.length`（本轮答对）分支里**没有清空 `mm.input`**，也没有移除 `input` class；`mm.input` 只在**下一次** `memShow` 的 1607 行才清空——而 `memShow` 是 `setTimeout(memShow, 620)` 之后才跑（1638）。`memPick` 开头只拦 `showing`（1620），不拦"已完成"。

于是 620ms 窗口内第二次点击 → `mm.input.push(i)` → `n = seq.length + 1` → 1626 行拿 `mm.seq[n-1]`（= `undefined`）比较 → 恒不相等 → **`memFail`，刚赢下的一轮变成失败**。

- **最小修复**：`memPick` 开头加 `if(mm.input.length >= mm.seq.length) return;`，并在答对分支清空 `mm.input`。约 2 行。

### 二-9｜🔴 LLM 输出安全过滤被绕过：机器人的 인사말/소개 未过滤

`server.js:409` 注释声明「**실제로 화면에 노출되는 모든 LLM 결과는 이 필터를 통과해야 한다**」——**与代码事实不符**。`sanitizeLine`/`isSafeText` 全树只有 **2 个调用点**：

```
675:  const safe = sanitizeLine(txt, 80);                              // /api/interact ✅
727:  const reaction = sanitizeLine(raw, 80) || '오늘 이야기…';        // /api/quest/answer ✅
```

而 **`generatePersonality`（server.js:330）直接把 LLM 返回的 `greeting`/`desc` 原样返回**：

```js
if(j.greeting && j.desc) return { personality: main, greeting: String(j.greeting).slice(0,60), desc: String(j.desc).slice(0,80) };
```

这两个字段会写进 `robots` 表并显示在孩子界面上（app.js:287）。  
→ **3 个 LLM 出口中有 1 个完全没有安全过滤**，而它恰恰是孩子第一次见到机器人时看到的第一句话。P0-4 的"强制层"并未覆盖全部出口。  
→ （XSS 层面是安全的：前端一律 `esc()`；问题在**内容安全**这一评价细则明文要求上。）

### 二-10｜🔴 상점 구매 버튼无进行中防护 → 消耗品被静默双重扣费

把两个购买入口对比：

```js
// 미리보기 모달 (1870-1872) — 有防护 ✅
```
